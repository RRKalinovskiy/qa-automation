# Написание проверки Saby по сценарию

## Когда использовать

- Нужно превратить требования, тест-сценарий или чек-лист в документ
  «Проверка» Saby.
- Нужно добавить этапы и пункты в существующую проверку.
- Нужно проверить, что структура проверки соответствует сценарию.
- Нужно проставить статусы пунктам по результатам тестирования.

Не используй этот навык для сделок, задач и других документов Saby —
для них есть отдельные навыки.

## Что понадобится

1. **MCP `saby-checks`** подключён в OpenCode. Проверь:
   `saby_check_statuses` без аргументов должен вернуть список статусов.
2. **Авторизация Saby.** Один раз выполни в терминале:

   ```bash
   npm run saby:login
   ```

   Откроется браузер; войди в Saby и дождись сообщения о сохранении.
   Сессия сохранится в `.auth/saby.json` (файл в `.gitignore`).
   Если MCP уже был запущен, перезапусти сессию OpenCode.
   Альтернатива для CI — переменная `SABY_COOKIE` с полной строкой Cookie.

3. **Ссылка на проверку** (или её id). Ссылка вида
   `https://online.sbis.ru/opendoc.html?guid=...&client=3`
   или `https://online.sbis.ru/doc/<guid>?client=3`.

4. **Сценарий**: требования, тест-кейсы или описание функционала.
   Если сценария нет — сначала используй навык `qa-scenario`.

## Модель проверки

```text
Проверка
├── Этап (функциональная область)
│   ├── ЧЛ (набор идей одного сценария)
│   ├── ТК (автотест)
│   └── Т (требование)
└── Этап
```

- **Этап** группирует проверки по области: «Карточка этапа»,
  «Карточка итога», «Мобильное приложение».
- **ЧЛ** — набор идей одного ручного сценария: например, валидация
  телефона и email. Минимум 2 шага/идеи.
- **ТК** — автотест: одна идея, покрытая кодом, с обязательным
  `automation`.
- **Т** — требование или критерий приёмки.
- Этап и пункт — один тип документа `ПунктПроверки`; иерархию задаёт
  `ЧеклистСтруктура.Раздел`.
- **Корневой этап** через API не создаётся. Новые этапы добавляются
  внутри существующего корневого этапа. Если в проверке нет корневых
  этапов — попроси пользователя добавить первый этап в UI.

Если нужна **новая проверка**, используй `saby_check_create`. Для неё
нужны `employeeId` и `departmentId` — возьми их из существующей проверки
через `saby_check_get` (поля `employeeId`/`departmentId`) или задай
`SABY_EMPLOYEE_ID`/`SABY_DEPARTMENT_ID`.

## ТК или ЧЛ: что выбрать

`ТК` и `ЧЛ` — не два названия одного и того же. Это разные единицы планирования.

| Тип | Что это | Когда использовать |
|---|---|---|
| `ТК` | **Тест-кейс**, обычно автотест | Нужен один тест-кейс с конкретным сценарием; ссылка на автотест не обязательна |
| `ЧЛ` | **Чек-лист**: набор идей одного ручного сценария | Несколько связанных проверок в одном блоке: например, валидация телефона и email |
| `Т` | Требование или критерий приёмки | Пункт фиксирует требование, а не проверку |

Правило по умолчанию — **ЧЛ**. Одна ручная идея не создаёт отдельный `ТК`:
она становится шагом уже существующего `ЧЛ`.

Для `ТК`:

- ссылка на автотест (`automation`) **не обязательна**;
- рекомендуется до **10 шагов**;
- если шагов больше 10 — предупреждение;
- если шагов больше 15 — тест стоит рассмотреть для дробления.

```text
Нужен один тест-кейс с конкретным сценарием?
├── Да → ТК; automation — если автотест уже есть
└── Нет → ручная проверка
    ├── Несколько идей одного сценария → один ЧЛ с шагами
    └── Одна идея → шаг существующего ЧЛ
```

`manual: true` помечает ТК как ручной: пометка будет ПК, а не АТ.

Почему `ЧЛ` в приоритете:

- проще читается и поддерживается;
- быстрее прогоняется;
- меньше эффекта пестицидов при повторных прогонах ПК;
- не плодит отдельные карточки на каждую идею.

Пример: `ТК: Неверный формат email` и `ТК: Неверный формат телефона` —
это одна идея «Валидация контактных данных». Правильно: один
`ЧЛ: Валидация контактных данных` с двумя шагами.

## Правила оформления тестов

1. **Название теста** всегда начинается с одного из префиксов:
   - `ТК` — тест-кейс, обычно автотест;
   - `ЧЛ` — чек-лист, набор идей одного ручного сценария;
   - `Т` — требование.

   Пример: `ЧЛ: Валидация контактных данных`.
   `ТК` не требует ссылки на автотест.
2. **Короткое описание, что проверяем**, заполняется в блоке
   «Общее описание» → **Комментарий**. Оно не должно совпадать с названием.
3. **Предварительные шаги** пишутся в блоке «Общее описание» → **Описание**.
4. В предварительных шагах — основные шаги подготовки к тесту
   (открыть карточку, подготовить роль, данные, инструмент).
5. **Предусловие** оформляется строго так:

   ```text
   ПРЕДУСЛОВИЕ:
   1. Открыть карточку ФЛ.
   2. Подготовить пользователя с ролью …
   ```

6. **Плановое время** — не более **5 минут** на сценарий. MCP обрезает
   большее значение до 5 и возвращает предупреждение.
7. **Пометки**:
   - флаг — **ПК** (по умолчанию для `ЧЛ`);
   - красный — **Важный МК**;
   - жёлтый — **Незначительный МК**;
   - зелёный — **МК не критичный функционал**;
   - синий — **АТ** (по умолчанию для `ТК`).
8. **Описание того, что делаем**, не должно совпадать с названием кейса.
9. **`ТК`**: `automation` не обязателен. Рекомендуется до 10 шагов;
   больше 15 — рассмотреть дробление теста.
10. **`ЧЛ`** содержит минимум 2 идеи/шага в рамках одного сценария.

Данные сценария не пишутся в поле статуса («Текущее состояние»).
Для этого есть отдельные поля: «Комментарий» и «Описание».

MCP проверяет префикс, комментарий, описание и лимит времени при создании
и обновлении теста. Получить правила программно:
`saby_check_rules`.

## Если проверка строится по проекту

Сначала изучи проект навыком `saby-project-research`:

```text
saby_project_get → saby_project_map → saby_project_requirements
→ saby_project_check_draft
```

Проект на `project.sbis.ru` — рабочий документ, его нельзя менять.
Черновик проверки создаётся только в памяти; после согласования его
передают в `saby_check_import_scenario` с `dryRun: true`.

## Алгоритм

### 1. Проверь доступ и карточку

```text
saby_check_get({ check: "<ссылка или id>" })
```

Убедись, что это нужная проверка: название, номер, шаблон, ссылка.
Если вернулась ошибка доступа — не продолжай запись.

### 2. Прочитай текущую структуру

```text
saby_check_tree({ check: "<ссылка или id>", depth: 2 })
```

Запомни:

- `structureId` корневых этапов — кандидаты в `parentSectionId`;
- существующие этапы и пункты — чтобы не создать дубли;
- `docId` — id для обновления и удаления;
- `statusId` — текущие статусы.

Если в разделе уже есть похожие пункты, сначала построй план слияния:

```text
saby_check_merge_plan({
  check: "<ссылка или id>",
  parentSectionId: <structureId этапа>,
  groups: [
    {
      targetName: "ЧЛ: Валидация контактных данных",
      pointIds: [<id ТК email>, <id ТК телефона>]
    }
  ]
})
```

Без `groups` инструмент сам покажет кандидатов по похожим названиям.
План ничего не меняет. Удаление исходных `ТК` — только после подтверждения
пользователя и переноса всех идей в `ЧЛ`.

### 3. Проверь статусы

```text
saby_check_statuses({ check: "<ссылка или id>" })
```

Не хардкодь id статусов: на другом стенде набор может отличаться.
Для новых пунктов используй «Не тестировался» (обычно 486).

### 4. Спроектируй проверку

Правила:

- **Этап = область или требование.** Не делай этап на каждый шаг.
- **`ТК` = один тест-кейс с конкретным сценарием.** Обычно автотест,
  но ссылка на код не обязательна. Держите до 10 шагов; больше 15 —
  дробите.
- **`ЧЛ` = один ручной сценарий с набором идей.** Валидация телефона и
  email — это два шага одного `ЧЛ`, а не два `ТК`.
- **Одна ручная идея** добавляется шагом в существующий `ЧЛ`.
- **Новый `ЧЛ`** — только для нового сценария или блока.
- **Название пункта** — короткое и конкретное:
  `ЧЛ: Валидация контактных данных`,
  `ТК: Поиск по описанию: пустой результат`.
- **Описание** — предусловие, шаги и ожидаемый результат:

  ```text
  ПРЕДУСЛОВИЕ:
  1. Открыть карточку ФЛ.
  2. Подготовить клиента с правами на редактирование.

  ШАГИ:
  1. Ввести телефон в неверном формате.
  2. Ввести email в неверном формате.

  ОЖИДАЕМЫЙ РЕЗУЛЬТАТ:
  Показаны сообщения валидации, данные не сохраняются.
  ```

- **Плановое время** — 2–5 минут на `ЧЛ`, не более 5.
- **Статус нового пункта** — «Не тестировался».
- **Тестовые данные** — только зарезервированные: `example.com`,
  телефоны `+1 555 …`. Никаких реальных персональных данных и секретов.

Если проверка не является песочницей, покажи пользователю план
(таблица «этап → пункты») и получи подтверждение перед записью.

### 5. Сухой прогон импорта

Собери JSON по формату из `reference/scenario-format.md` и вызови:

```text
saby_check_import_scenario({
  check: "<ссылка или id>",
  parentSectionId: <structureId корневого этапа>,
  sections: [...],
  dryRun: true
})
```

Проверь `plan`, `warnings`, `totalPoints`. Если есть дубли — реши,
переиспользовать их или обновить (`updateExisting`).

### 6. Запись

Для массового сценария используй импорт. Для точечных правок есть
`saby_check_stage_create`, `saby_check_point_create`,
`saby_check_point_update`.

```text
saby_check_import_scenario({
  check: "<ссылка или id>",
  parentSectionId: <structureId корневого этапа>,
  sections: [...],
  dryRun: false,
  onExisting: "reuse",
  updateExisting: false,
  cleanupOnError: true
})
```

По умолчанию:

- существующие этапы и пункты **переиспользуются**;
- существующие пункты **не обновляются**;
- при ошибке созданные в этом вызове объекты удаляются.

Не ставь `updateExisting: true` без запроса пользователя.

### 7. Проверь результат

```text
saby_check_verify({
  check: "<ссылка или id>",
  expected: { sections: [{ name: "Этап", points: ["Пункт 1", "Пункт 2"] }] },
  strict: false
})
```

`ok: true` — все ожидаемые пункты на месте. Если `missing` не пуст,
не утверждай, что проверка готова.

Отдельный пункт можно перечитать через:

```text
saby_check_point_get({ pointId: <docId> })
```

### 8. Отчёт

Сообщи пользователю:

- ссылку на проверку;
- сколько этапов и пунктов создано/переиспользовано;
- id созданных объектов (если нужно для удаления);
- предупреждения (`warnings`);
- что осталось за пределами автоматизации (ручные шаги, вложения).

## Формат сценария

Кратко:

```json
{
  "sections": [
    {
      "name": "Карточка клиента: контактные данные",
      "description": "Требования: валидация телефона и email.",
      "plannedMinutes": 30,
      "points": [
        {
          "type": "ЧЛ",
          "name": "ЧЛ: Валидация контактных данных",
          "comment": "Проверяем реакцию системы на невалидные телефон и email.",
          "precondition": [
            "Открыть карточку ФЛ.",
            "Подготовить клиента с правами на редактирование."
          ],
          "steps": [
            "Ввести телефон в неверном формате.",
            "Ввести email в неверном формате."
          ],
          "expected": "Показаны сообщения валидации, данные не сохраняются.",
          "plannedMinutes": 5,
          "status": "Не тестировался",
          "mark": "pc"
        }
      ]
    }
  ]
}
```

Полная схема и пример — `reference/scenario-format.md`.
Готовый демо-сценарий — `docs/scenarios/saby-checks-demo.md`.

## Статусы

| Когда ставить | Статус |
|---|---|
| Пункт только создан | Не тестировался |
| Идёт ручная проверка | В процессе тестирования |
| Проверка пройдена | Тестирование проведено |
| Найдены дефекты | Выпускаем с ошибками |
| Покрыт автотестом | Автотест пройден |
| Автотест упал | Автотест не пройден |
| Ждём исправления | Ожидаем исправления |
| Проверять не нужно | Не проверяем |

Не меняй статусы существующих пунктов без явного запроса: это может
исказить статистику команды.

## Безопасность

- Не удаляй проверку и существующие пункты без явного подтверждения.
- `saby_check_item_delete` — только для объектов, созданных в этом
  прогоне; обязателен `confirm: true`. Для этапа с пунктами используй
  `recursive: true` (дочерние удаляются первыми).
- `saby_check_merge_plan` — только чтение. Покажи план пользователю до
  любых переименований и удалений.
- Не создавай корневые этапы: API возвращает внутреннюю ошибку.
- Не записывай в проверку секреты, токены и реальные персональные данные.
- Не используй `updateExisting: true` на чужой проверке.
- Если сомневаешься — сначала `dryRun: true` и вопрос пользователю.

## Ошибки

| Симптом | Что делать |
|---|---|
| «Нет авторизации в Saby» | `npm run saby:login` или задать `SABY_COOKIE` |
| «Документ недоступен» | Проверить ссылку/доступ; возможно, документ удалён |
| «Внутренняя ошибка сервера» при создании | Проверить `parentSectionId`, формат даты `YYYY-MM-DD`, шаблон |
| «Неизвестный статус» | `saby_check_statuses`, передать id или точное название |
| «ЧЛ — набор идей» | меньше 2 шагов | добавить идеи или влить в существующий `ЧЛ` |
| Предупреждение о длинном ТК | больше 10 шагов | проверить; больше 15 — разделить тест |
| Пункт создан, но не виден | Проверить `parentSectionId` и `saby_check_tree` |
| Дубли этапов/пунктов | `onExisting: "reuse"`, не создавать повторно |

## Чек-лист

- [ ] Проверка открыта через `saby_check_get`, это нужный документ.
- [ ] `saby_check_tree` прочитан, дубли исключены.
- [ ] Для похожих пунктов построен `saby_check_merge_plan` и согласован.
- [ ] Тип выбран верно: `ЧЛ` для набора идей, `ТК` для одного тест-кейса.
- [ ] В `ТК` до 10 шагов; если больше 15 — тест разделён или согласован.
- [ ] Каждый `ЧЛ` содержит минимум 2 идеи/шага одного сценария.
- [ ] Статусы получены через `saby_check_statuses`.
- [ ] Каждый пункт имеет шаги и ожидаемый результат.
- [ ] Нет реальных персональных данных и секретов.
- [ ] `dryRun` показан пользователю (если проверка не песочница).
- [ ] Импорт выполнен с `cleanupOnError: true`.
- [ ] `saby_check_verify` вернул `ok: true`.
- [ ] Пользователю отданы ссылка, counts, warnings.
