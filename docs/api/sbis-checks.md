# Saby: проверки (`Проверка`, `ПунктПроверки`)

Документ описывает JSON-RPC контракты веб-клиента Saby для документа
«Проверка»: чтение карточки, структура этапов и пунктов, создание, изменение
полей, смена статуса и удаление.

**Стенд:** `https://online.sbis.ru`
**Версия клиента:** `26.5118-135`
**Дата исследования:** 29.10.2026
**Песочница:** проверка № 9734, `guid=01a163d8-bdf4-74c1-8905-341123ff78ce`,
`@Документ=632121183`
**Пример:** проверка проекта № 2607,
`guid=019e878e-855b-79ac-ba05-567118e87ccc`

> Практическая реализация контрактов — MCP `mcp/saby-checks`
> (инструменты `saby_check_*`). Навыки: `saby-checks` (написание проверки)
> и `saby-checks-api` (поддержка MCP). Авторизация: `npm run saby:login`.

## 1. Статусы проверки контрактов

| Статус | Значение |
|---|---|
| ✅ | Метод вызван напрямую, ответ `200`, структура и побочный эффект проверены |
| ⚠️ | Метод снят с трафика UI, прямой вызов с полным контрактом не повторялся |
| ❓ | Метод существует, но контракт не подтверждён |

## 2. Модель объекта

```text
Проверка (документ, ТипДокумента = 2707)
└── ЧеклистСтруктура (корень проверки)
    ├── Этап / раздел (ПунктПроверки, Раздел@ = true)
    │   ├── Пункт (ПунктПроверки, Раздел@ = null)
    │   └── Вложенный этап
    └── Пункт верхнего уровня
```

Важно:

- «Этап» и «пункт» — это один тип документа `ПунктПроверки` (id типа `2745`).
- Иерархию задаёт `ЧеклистСтруктура.Раздел` — **id структуры родителя**,
  а не id документа.
- У каждого пункта есть два идентификатора:
  - `Документ` — id документа (`@Документ`), по нему идут `ПрочитатьДляУчастника`,
    `Записать`, `УдалитьДокументы`;
  - `@ЧеклистСтруктура` — id структуры, по нему строятся дочерние элементы
    и читается список.
- Корневой этап создаётся только через UI. Прямой `ПунктПроверки.Создать`
  с `Раздел = null` возвращает внутреннюю ошибку. Новые этапы создаются
  внутри существующего корневого этапа.

## 3. Транспорт

```
POST https://online.sbis.ru/service/?x_version=26.5118-135
```

Авторизация — сессионные cookie (`credentials: include`), отдельного токена нет.

Конверт:

```json
{
  "jsonrpc": "2.0",
  "protocol": 7,
  "method": "<Сервис.Метод>",
  "params": {},
  "id": 1
}
```

Заголовки:

| Заголовок | Значение |
|---|---|
| `content-type` | `application/json; charset=UTF-8` |
| `x-adaptive` | `false` |
| `x-requested-with` | `XMLHttpRequest` |
| `x-calledmethod` | латиница, например `PunktProverki.Sozdat` |
| `x-originalmethodname` | `base64(UTF-8("<Кириллица>.<Метод>"))` |
| `x-saby-appid` | `d7b1d6a5-e59d-4b03-b823-726fbdc35d09` |
| `x-saby-appversion` | `26.5118` |
| `x-saby-cfgid` | `2725babf-70e1-4f04-8e78-1b4272de7b21` |
| `x-lastmodification` | метка времени, например `2026-10-29T104411.400646+03` |
| `x-osversion` | `OSType=Windows;OSVersion=10.0;IsWin11=true` |

Без `x-lastmodification` часть методов возвращает `404` с сообщением
«Внутренняя ошибка сервера». Это не отсутствие метода, а отказ маршрутизации.

## 4. Формат record

```json
{
  "_type": "record",
  "f": 0,
  "s": [
    { "n": "@Документ", "t": "Число целое" },
    { "n": "ЧеклистСтруктура.Название", "t": "Строка" }
  ],
  "d": [633433276, "MCP проверка"]
}
```

- `s` — схема: имя и тип;
- `d` — значения в том же порядке;
- `recordset` — `d` содержит массив строк;
- вложенные записи и выборки передаются такими же объектами.

## 6. Чтение проверки

### 6.1. Как получить числовой id по ссылке

JSON-RPC работает с числовым `@Документ`, а ссылка содержит `guid`.
Страница `/doc/<guid>` отдаёт SSR-состояние, в котором есть числовой id:

```js
const html = await fetch(`/doc/${guid}?client=3`).then((r) => r.text());
const id = Number(html.match(/"entityKey":"(\d+)"/)[1]);
```

Для проверки № 9734 это `632121183`.

### 6.2. `Проверка.ПрочитатьДляУчастника` ✅

```json
{
  "method": "Проверка.ПрочитатьДляУчастника",
  "params": {
    "ИдО": 632121183,
    "ИмяМетода": "Проверка.Список",
    "ДопПоля": { "ИмяОбъекта": "Проверка" }
  }
}
```

Ответ — `record` с 230 колонками. Ключевые поля:

| Поле | Значение (пример) |
|---|---|
| `@Документ` | `632121183` |
| `ИдентификаторДокумента` | `01a163d8-bdf4-74c1-8905-341123ff78ce` |
| `Номер` / `ЧисловойНомер` | `"9734"` / `9734` |
| `ДокументРасширение.Название` | `"Тест AI"` |
| `РазличныеДокументы.ИнформацияJSON` | `[["p",{"version":"2"},"Тест AI"]]` |
| `ОбъектПланирования.@ОбъектПланирования` | `485` (шаблон) |
| `ОбъектПланирования.Название` | `"Тестирование проекта"` |
| `Сотрудник` / `Подразделение` | `49067454` / `58470437` |
| `ЧеклистСтруктура.@ЧеклистСтруктура` | `306845363` — корень структуры |
| `Дата` / `Время` | `"2026-10-22"` / `"16:41:50.754"` |
| `Удален` | `false` |

## 8. Создание проверки

### 8.1. `Проверка.Создать` ✅

```json
{
  "method": "Проверка.Создать",
  "params": {
    "Фильтр": {
      "_type": "record", "f": 0,
      "d": [true, 49067454, 58470437, 49067454, "Проверка", 485,
            "2026-10-29", "11:00:00.000"],
      "s": [
        { "n": "ВызовИзБраузера", "t": "Логическое" },
        { "n": "ЛицоСоздал", "t": "Число целое" },
        { "n": "Подразделение", "t": "Число целое" },
        { "n": "Сотрудник", "t": "Число целое" },
        { "n": "ТипДокумента.ТипДокумента", "t": "Строка" },
        { "n": "ОбъектПланирования", "t": "Число целое" },
        { "n": "Дата", "t": "Дата" },
        { "n": "Время", "t": "Время" }
      ]
    },
    "ИмяМетода": "Проверка.Список"
  }
}
```

- `ОбъектПланирования = 485` — шаблон «Тестирование проекта».
- `Дата` — ISO `YYYY-MM-DD`, не `DD.MM.YYYY`.
- Ответ — `record` созданной проверки; `d[0]` — числовой id.
- Проверено: создание без проекта работает, но название по умолчанию
  «Проверка проекта». Название задаётся отдельно.

### 8.2. `Проверка.Записать` ✅

Частичная запись, как у сделки. Обязателен `@Документ`:

```json
{
  "method": "Проверка.Записать",
  "params": {
    "Запись": {
      "_type": "record", "f": 0,
      "d": [632121183, "Тест AI",
            "[[\"p\",{\"version\":\"2\"},\"Тест AI\"]]"],
      "s": [
        { "n": "@Документ", "t": "Число целое" },
        { "n": "ДокументРасширение.Название", "t": "Строка" },
        { "n": "РазличныеДокументы.ИнформацияJSON", "t": "Строка" }
      ]
    }
  }
}
```

Чтобы название отобразилось в шапке, обновляйте **оба** поля:
`ДокументРасширение.Название` и `РазличныеДокументы.ИнформацияJSON`.

### 9.1. `ПунктПроверки.Создать` ✅

Общий контракт:

```json
{
  "method": "ПунктПроверки.Создать",
  "params": {
    "Фильтр": {
      "_type": "record", "f": 0,
      "d": [true, 49067454, 58470437, 49067454, "ПунктПроверки",
            632121183, 306974729, false, false,
            "2026-10-29", "10:51:33.223"],
      "s": [
        { "n": "ВызовИзБраузера", "t": "Логическое" },
        { "n": "ЛицоСоздал", "t": "Число целое" },
        { "n": "Подразделение", "t": "Число целое" },
        { "n": "Сотрудник", "t": "Число целое" },
        { "n": "ТипДокумента.ТипДокумента", "t": "Строка" },
        { "n": "ЧеклистСтруктура.БазовыйРаздел", "t": "Число целое" },
        { "n": "ЧеклистСтруктура.Раздел", "t": "Число целое" },
        { "n": "ЧеклистСтруктура.Раздел$", "t": "Логическое" },
        { "n": "ЧеклистСтруктура.Раздел@", "t": "Логическое" },
        { "n": "Дата", "t": "Дата" },
        { "n": "Время", "t": "Время" }
      ]

    "ИмяМетода": "ПунктПроверки.Список"

```

Флаги:

| Создаём | `Раздел$` | `Раздел@` |
|---|---|---|
| Пункт | `false` | `false` |
| Этап (раздел) | `true` | `true` |

`ЧеклистСтруктура.Раздел` — id структуры родителя.
`ЧеклистСтруктура.БазовыйРаздел` — id проверки.

Ответ:

- для пункта — число (id документа);
- для этапа — `record`, где `d[0]` — id документа.

Проверено: создание этапа внутри корневого этапа и пункта внутри этапа.

### 9.2. `ПунктПроверки.Записать` ✅

Частичная запись. Обязателен `@Документ`:

```json
{
  "method": "ПунктПроверки.Записать",
  "params": {
    "Запись": {
      "_type": "record", "f": 0,
      "d": [633433276, "MCP проверка partial",

      "s": [
        { "n": "@Документ", "t": "Число целое" },
        { "n": "ЧеклистСтруктура.Название", "t": "Строка" },
        { "n": "ЧеклистСтруктура.Версия", "t": "Строка" },
        { "n": "ЧеклистСтруктура.ПлановоеВремя", "t": "Строка" },
        { "n": "ЧеклистСтруктура.ОбъектПланирования", "t": "Число целое" }
      ]
    }
  }
}
```

Поля:

| Поле | Назначение |
|---|---|
| `ЧеклистСтруктура.Название` | название пункта |
| `ЧеклистСтруктура.Версия` | описание / требования |
| `ЧеклистСтруктура.ПлановоеВремя` | ISO-длительность, `P0DT0H10M0S` |
| `ЧеклистСтруктура.ОбъектПланирования` | id статуса |
| `ЧеклистСтруктура.Лицо` | ответственный (id сотрудника) |

Ответ — id документа. После записи перечитывайте `ПрочитатьДляУчастника`.

## 11. Удаление

### 11.1. Удаление из структуры — `ПунктПроверки.Remove` ✅

Для пунктов и этапов используйте `Remove` с **id структуры**
(`@ЧеклистСтруктура`), а не с id документа:

```json
{
  "method": "ПунктПроверки.Remove",
  "params": { "ИдО": [307609331] }
}
```

Ответ: `true`. Именно этот метод удаляет узел из структуры и
пересчитывает `КолВо`. Если удалить только документ через
`Документ.УдалитьДокументы`, ссылка в структуре останется и счётчик
этапа будет завышен.

Для этапа с вложенными пунктами удаляйте дочерние структуры первыми
(снизу вверх), затем сам этап.

### 11.2. Удаление документа

```json
{
  "method": "Документ.УдалитьДокументы",
  "params": { "ИдО": [633433276] }
}
```

Ответ:

```json
{
  "_type": "record", "f": 0,
  "s": [
    { "n": "УдаленыВКорзину", "t": { "n": "Массив", "t": "Число целое" } },
    { "n": "УдаленыНасовсем", "t": { "n": "Массив", "t": "Число целое" } }
  ],
  "d": [[633433276], []]
}
```

После удаления `Удален = true`. Восстановление — `Документ.Восстановить`
с `{ "ключДокумента": <id> }` ⚠️ (на проверке не повторялось).

> Для проверки целиком используйте `Документ.УдалитьДокументы` с id
> проверки. Для пунктов/этапов — `ПунктПроверки.Remove` с id структуры.

## 12. Полный сценарий записи

1. `GET /doc/<guid>?client=3` → числовой id проверки.
2. `Проверка.ПрочитатьДляУчастника` → шаблон, ответственный, корень структуры.
3. `ПунктПроверки.СписокПунктовПроверки` (корень) → существующие этапы.
4. `ПунктПроверки.Создать` с `Раздел$=true`, `Раздел@=true` → новый этап.
5. `ПунктПроверки.Записать` → название и описание этапа.
6. `ПунктПроверки.Создать` с `Раздел$=false`, `Раздел@=false` → новый пункт
   внутри этапа.
7. `ПунктПроверки.Записать` → название, описание, плановое время, статус.
8. `ПунктПроверки.СписокПунктовПроверки` (дочерние) → проверка результата.
9. При необходимости `Проверка.МассовоеИзменениеСтатусаИзПМО`.
10. Удаление тестовых пунктов/этапов — `ПунктПроверки.Remove` по id
    структуры (дети раньше родителя).

## 13. Методология ТК/ЧЛ и слияние дублей

Тип пункта не хранится отдельным полем — он определяется префиксом названия.

| Префикс | Смысл | Условие |
|---|---|---|
| `ТК` | тест-кейс, обычно автотест | `automation` не обязателен; до 10 шагов рекомендуется, больше 15 — повод для дробления |
| `ЧЛ` | набор идей одного ручного сценария | минимум 2 идеи/шага |
| `Т` | требование | — |

Правило по умолчанию — `ЧЛ`. `ТК` — один тест-кейс, обычно автотест;
ссылка на автотест не обязательна. `manual: true` помечает ручной `ТК`
(пометка ПК вместо АТ). Если в `ТК` больше 10 шагов — предупреждение;
больше 15 — тест стоит рассмотреть для дробления.

`automation` не имеет отдельного поля. MCP добавляет его в
`ЧеклистСтруктура.Описание` блоком:

```text
АВТОТЕСТ:
tests/ui/client-card.spec.ts
```

Пометки MCP только рекомендует: `pc` для `ЧЛ`, `automated` для `ТК`.
Частичная запись `Пометки` игнорируется, поэтому выставлять их нужно в UI
или полной записью документа.

Перед слиянием используйте read-only `saby_check_merge_plan`:

```json
{
  "check": "<ссылка или id>",
  "parentSectionId": 123,
  "groups": [
    {
      "targetName": "ЧЛ: Валидация контактных данных",
      "pointIds": [101, 102]
    }
  ]
}
```

Инструмент возвращает `groups[].actions`: создать `ЧЛ`, добавить шаги,
удалить исходные `ТК` (с `requiresConfirm: true`), а также `warnings`.
Без `groups` он ищет кандидатов по похожим названиям. План ничего не
меняет. Удаление исходных `ТК` — только после подтверждения пользователя
и проверки, что все идеи перенесены.

Перенос `TestCase`-шагов, предусловий и пометок пока не автоматизирован:
план работает с идеями из «Комментария» и требует ручной проверки в UI.

## 14. Ограничения и открытые вопросы

1. **Корневой этап.** Прямое создание с `Раздел = null` возвращает
   «Внутренняя ошибка сервера». Этапы создаются внутри существующего
   корневого этапа. Корневые этапы добавляются в UI.
2. **Проект проверки.** Проверка создаётся без проекта, но в примере
   у неё есть «Проект разработки». Привязка к проекту в контракте
   `Проверка.Создать` не подтверждена.
3. **Шаблон.** `ОбъектПланирования = 485` — «Тестирование проекта».
   Для другого шаблона id нужно получить из UI/справочника.
4. **Порядок.** Поле `ЧеклистСтруктура.ПорНомер` читается, но метод
   перемещения/сортировки не исследован.
5. **Вложения и шаги.** `ПунктПроверки.AttachList` и `TestCase.СписокШагов`
   замечены в трафике, но запись шагов/вложений не проверялась.
6. **Статусы.** Набор id может зависеть от конфигурации стенда.
   Перед записью читайте `СтатистикаПоПроверке`.
7. **Права.** Часть операций зависит от роли и лицензии. Ошибка
   «Документ недоступен» может означать и удаление, и отсутствие доступа.
