# Тестовые данные

Стратегия данных проекта. Данные живут отдельно от сценариев и кода тестов.

## Принципы

1. **Уникальность.** Каждый прогон создаёт свои сущности: префикс `qa-` + короткий UUID.
2. **Изоляция.** Тесты не делят изменяемые данные и не зависят от порядка запуска.
3. **Воспроизводимость.** Данные создаются кодом или API, а не руками на стенде.
4. **Очистка.** У каждого набора есть владелец и способ удаления; teardown обязателен.
5. **Безопасность.** Никаких реальных персональных данных и секретов в репозитории.

## Классы данных

| Класс | Пример | Где хранить |
|---|---|---|
| Справочные | страны, валюты, статусы | константы в `src/data/` |
| Генерируемые | email, имена, номера | фабрики в `src/data/factories/` |
| Сид-данные | предзаполненные сущности стенда | `docs/test-data/` + env |
| Секреты | токены, пароли | `.env` |

## Идентификаторы

- Набор данных: `TD-<AREA>-<NNN>`.
- Фабрика: `build<Entity>()` с `Partial<Entity>` для переопределений.
- Файл описания набора: `docs/test-data/<area>.md`.

## Правила

- Email — только `example.com` (`qa+<id>@example.com`).
- Телефоны — только зарезервированный диапазон `+1 555 …`.
- Пароли — генерируются, соответствуют политике стенда, не переиспользуются между наборами.
- Значения, влияющие на бизнес-логику (суммы, лимиты, даты), задаются явно в сценарии.
- Для чувствительных полей маскируй значения в отчётах и логах.

## Очистка

- Удалять через API в `afterAll`/`afterEach`, даже если тест упал.
- Если API удаления нет — использовать отдельный тестовый аккаунт и помечать данные префиксом `qa-`.
- Не удалять общие справочники и сид-данные.
