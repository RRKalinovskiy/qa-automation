# Исследование проекта Saby

## Когда использовать

- Нужно понять проект перед тестированием: этапы, сроки, ответственные,
  документы.
- Нужно вытащить требования (Т) из технического задания или другого
  SabyDoc.
- Нужно построить карту функционала «этап → требования → документы».
- Нужно сформировать первичную проверку по проекту.

## Главное правило безопасности

**Проект — рабочий документ. Его нельзя менять.**

Через этот навык разрешены только чтение и построение черновиков:

- `saby_project_get`
- `saby_project_documents`
- `saby_project_document_read`
- `saby_project_requirements`
- `saby_project_map`
- `saby_project_check_draft`

Запрещено:

- вызывать `create`/`update`/`delete` для проекта, этапа, задачи,
  документа или участника;
- менять поля, статусы, пометки, сроки, состав участников;
- «поправить» документ, даже если в нём ошибка.

Если для проверки нужны изменения — сначала опиши их пользователю и
получи отдельное подтверждение. Изменения в проекте не входят в этот
навык.

## Инструменты

| Инструмент | Что делает |
|---|---|
| `saby_project_get` | карточка проекта: название, описание, статус, сроки, этапы |
| `saby_project_documents` | список документов проекта: `attachId`, название, тип, редакция |
| `saby_project_document_read` | текст SabyDoc, оглавление и извлечённые требования |
| `saby_project_requirements` | требования из ТЗ и других SabyDoc |
| `saby_project_map` | этапы + документы + требования + привязка к этапам |
| `saby_project_check_draft` | черновик проверки: этапы → пункты `Т` |

Все инструменты read-only. Они не вызывают запись в проект.

## Алгоритм

### 1. Прочитай проект

```text
saby_project_get({ project: "<ссылка project.sbis.ru/uuid/...>" })
```

Зафиксируй:

- название, описание, статус, сроки;
- ответственного и подразделение;
- список этапов и их даты.

### 2. Прочитай документы

```text
saby_project_documents({ project: "<ссылка>" })
```

Ищи в первую очередь:

- `Техническое задание`;
- `Логическое описание макета`;
- `План тестирования`;
- описания «было/стало».

Если ТЗ нет — не выдумывай требования. Зафиксируй пробел и спроси, где
искать требования.

### 3. Прочитай SabyDoc

```text
saby_project_document_read({
  project: "<ссылка>",
  document: "Техническое задание",
  maxChars: 20000
})
```

Возвращает:

- `text` — текст документа;
- `headings` — оглавление;
- `requirements` — разделы и требования-утверждения;
- `truncated` — обрезан ли текст.

Если документ не SabyDoc (PDF, Word, ссылка), инструмент вернёт ошибку
или пустой текст. Это отдельный источник, его нужно обрабатывать другим
способом; не выдавай его за прочитанный.

### 4. Извлеки требования

```text
saby_project_requirements({
  project: "<ссылка>",
  maxDocuments: 3,
  maxRequirements: 60
})
```

Правила:

- раздел ТЗ уровня 1–2 — верхнеуровневое `Т`;
- абзац с «должен / необходимо / нужно / требуется» — уточняющее `Т`;
- у каждого требования должен быть источник: документ + раздел;
- `confidence: heading` — раздел, `confidence: text` — эвристика;
- не добавляй требования, которых нет в тексте;
- если требование непонятно или противоречит другому — вынеси в вопросы.

### 5. Построй карту функционала

```text
saby_project_map({
  project: "<ссылка>",
  includeDocuments: true,
  includeRequirements: true
})
```

Сопоставь:

```text
Этап проекта → документы → требования → что проверять
```

Если требование не привязалось к этапу, оно попадёт в
`unassignedRequirements`. Не скрывай такие требования: вынеси их в
отдельный блок «Требует уточнения».

### 6. Сформируй черновик проверки

```text
saby_project_check_draft({
  project: "<ссылка>",
  categories: ["ui", "general"],
  maxRequirements: 30,
  maxPerSection: 12
})
```

По умолчанию в черновик попадают функциональные требования (`ui` и
`general`). Технические (`technical`) добавляются только по запросу.

Инструмент создаёт только JSON-черновик:

- этапы проекта → этапы проверки;
- требования → пункты `Т: ...`;
- у пункта есть источник, комментарий и описание.

Он **ничего не создаёт в Saby**. Покажи черновик пользователю.

### 7. Создание проверки — только после согласования

Если пользователь подтвердил черновик:

1. `saby_check_import_scenario` с `dryRun: true`;
2. показать план;
3. после подтверждения — `dryRun: false`.

Создаётся новая проверка, а не изменение проекта.

## Формат отчёта

```text
Проект: <название>
Ссылка: <url>

Этапы:
| Этап | Сроки | Ответственный | Задачи |

| Документ | Тип | Дата | Редакция |

Требования:
| ID | Требование | Источник | Уверенность |

| Этап | Требования | Что проверять |

Вопросы:
1. ...
```

## Ошибки

| Симптом | Что делать |
|---|---|
| Нет авторизации | `npm run saby:login` или `SABY_COOKIE`; для project.sbis.ru — `SABY_PROJECT_COOKIE`, если cookies отличаются |
| Проект не найден | Проверить uuid/ссылку, права доступа |
| Документ не SabyDoc | Не выдавать его за прочитанный; запросить текст или другой источник |
| Требования не найдены | Проверить ТЗ, `saby_project_document_read`; зафиксировать пробел |
| Этап не сопоставлен | Оставить в `unassignedRequirements`, вынести вопрос |
| Текст обрезан | Увеличить `maxChars` или читать документ частями |

## Чек-лист

- [ ] Проект прочитан, это нужный документ.
- [ ] Этапы и документы зафиксированы.
- [ ] ТЗ/требования прочитаны, источник у каждого требования.
- [ ] Нет выдуманных требований.
- [ ] Несопоставленные требования вынесены отдельно.
- [ ] Черновик проверки показан пользователю.
- [ ] В проект не было ни одной записи.
