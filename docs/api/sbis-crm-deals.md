# Saby CRM: методы работы со сделками (`crm-deals`)

Документ описывает JSON-RPC методы, которые веб-клиент Saby использует на странице
`https://fix-online.sbis.ru/page/crm-deals/` для CRUD сделок, их композиции и операций
жизненного цикла: смена этапа, откат, смена ответственного, удаление, восстановление,
согласование, связывание документов.

**Стенд:** `fix-online.sbis.ru`
**Учётная запись:** `crmviewer / <пароль из .env>`
**Версия клиента:** `26.5120`
**Дата исследования:** 28.10.2026
**Тестовая сделка:** `56224` (№ 1800, тема «АТ Тема 20 этапов 5+5 20261026-174322»)

## Статусы проверки

| Статус | Значение |
|---|---|
| ✅ | Метод вызван напрямую, ответ `200` и ожидаемая структура зафиксированы |
| ⚠️ | Метод зафиксирован в трафике веб-клиента, но прямой вызов с подобранными параметрами не выполнялся |
| ❓ | Метод существует (сервер его знает), но контракт параметров не подтверждён |

## 1. Транспорт

### 1.1. Endpoint

```
POST https://fix-online.sbis.ru/service/?x_version=26.5120-78
```

Авторизация — сессионные cookie (`credentials: include`). Токен в заголовке не передаётся.

### 1.2. Конверт JSON-RPC

```json
{
  "jsonrpc": "2.0",
  "protocol": 7,
  "method": "<Сервис.Метод>",
  "params": { },
  "id": 1
}
```

`protocol: 7` — версия протокола Saby. Ответ содержит `result` либо `error`.

### 1.3. Заголовки

| Заголовок | Значение | Назначение |
|---|---|---|
| `content-type` | `application/json; charset=UTF-8` | Тип тела |
| `x-requested-with` | `XMLHttpRequest` | Признак AJAX |
| `x-adaptive` | `false` | Отключает адаптивный режим; часть документных методов без него не маршрутизируется |
| `x-calledmethod` | `Lid.ProchitatDlyaUchastnika` | Латиница: сервис + метод |
| `x-originalmethodname` | `base64(UTF-8("Лид.ПрочитатьДляУчастника"))` | Исходное имя (кириллица + латиница) |
| `x-saby-appid` | `d7b1d6a5-e59d-4b03-b823-726fbdc35d09` | Идентификатор приложения |
| `x-saby-appversion` | `26.5120` | Версия приложения |
| `x-saby-cfgid` | `2725babf-70e1-4f04-8e78-1b4272de7b21` | Идентификатор конфигурации |

Правило кодирования `x-originalmethodname`: в base64 кладётся UTF-8 строка
`"<Кириллический сервис>.<Метод>"`. Пример:

```
"Документ.CheckUnique" -> 0JTQvtC60YPQvNC10L3Rgi5DaGVja1VuaXF1ZQ==
```

`x-calledmethod` при этом содержит `Dokument.CheckUnique`.

### 1.4. Формат записей Saby

Saby сериализует записи (record/recordset) не в JSON-объекты, а в плоские структуры:

```json
{
  "_type": "record",
  "f": 0,
  "d": [56224, "АТ: запись через RPC"],
  "s": [
    { "n": "@Документ", "t": "Число целое" },
    { "n": "Примечание", "t": "Строка" }
  ]
}
```

- `s` — схема: `n` имя поля, `t` тип;
- `d` — значения в порядке `s`;
- `f` — версия/индекс формата;
- `_type` — `record` или `recordset`.

Для `recordset` в `d` лежит массив строк, а `s` описывает колонки.
Вложенные записи и выборки передаются такими же объектами.

### 1.5. Рабочий helper (page context)

```js
const call = async (latin, method, params) => {
  const resp = await fetch("/service/?x_version=26.5120-78", {
    method: "POST",
    credentials: "include",
    headers: {
      "content-type": "application/json; charset=UTF-8",
      "x-adaptive": "false",
      "x-requested-with": "XMLHttpRequest",
      "x-calledmethod": latin,
      "x-originalmethodname": btoa(
        String.fromCharCode(...new TextEncoder().encode(method))
      ),
      "x-saby-appid": "d7b1d6a5-e59d-4b03-b823-726fbdc35d09",
      "x-saby-appversion": "26.5120",
      "x-saby-cfgid": "2725babf-70e1-4f04-8e78-1b4272de7b21",
    },
    body: JSON.stringify({ jsonrpc: "2.0", protocol: 7, method, params, id: 1 }),
  });
  return resp.json();
};
```

Сделка — это документ `Лид` поверх общей сущности `Документ`.

| Номер | `Номер` / `ЧисловойНомер` | `"1800"` / `1800` |
| UUID документа | `ИдентификаторДокумента` | `01a181ba-044a-7675-98e5-aba26a4a37bf` |
| Тип | `ТипДокумента` | `50` (`"Лид"`) |
| Тема (регламент) | `Лид.Регламент` | `28510116` |
| Этап (фаза) | `Лид.Фаза` | `26168707` («Новый») |
| Переход | `Лид.Переход` | `null` |
| Клиент | `Лид.Контрагент` | `3722885` («Астартес CRM») |
| Ответственный | `Лид.Сотрудник` | `3722874` («Астартес C.») |
| Подразделение | `Лид.Подразделение` | `384` |
| Дата/время | `Дата` / `Время` | `2026-10-28` / `11:56:54.236` |

| Статус (этап) | `Статус` | `"Новый"` |

## 4. CRUD

### 4.1. Настройки типа документа — `Лид.TypeSettings` ✅

```json
{
  "method": "Лид.TypeSettings",
  "params": { "params": { "docType": "Лид" } }
}
```

Ответ — две записи: настройки отображения (`d[0]`) и настройки типа документа (`d[1]`).
Ключевое — привязки методов в `d[1].source.binding`:

```json
{
  "create": "Создать",
  "read": "ПрочитатьДляУчастника",
  "update": "Записать",
  "destroy": "Документ.УдалитьДокументы",
  "format": "Лид.ListCard"
}
```

Отсюда видно, что CRUD-операции — это методы сервиса `Лид`, а удаление делегировано
сервису `Документ`.

### 4.2. Создание — `Лид.Создать` ✅

Сделка `56224` создана этим методом. Параметры — запись с полями создаваемого лида:

```json
{
  "method": "Лид.Создать",
  "params": {
    "Запись": {
      "_type": "record",
      "f": 0,
      "d": [3722885, 28510116, "АТ Тема 20 этапов 5+5 20261026-174322"],
      "s": [
        { "n": "Лид.Контрагент", "t": "Число целое" },
        { "n": "Лид.Регламент", "t": "Число целое" },
        { "n": "Тема", "t": "Строка" }
      ]
    }
  }
}
```

Ответ — идентификатор созданной сделки (`56224`).

Перед созданием клиент проверяет дубли:

```
Lid.GetExisting
{ "params": { "Client": 3722885, "Regulation": 28510116,
              "CalcSettings": ["multilead", "black_list"] } }
```

Ответ: `{ ExistDoc: { Id }, Settings: { multilead, black_list } }`.
Если `multilead = false` и найден `ExistDoc.Id`, создание блокируется предупреждением.

### 4.5. Изменение — `Лид.Записать` ✅

Метод принимает частичную запись: обязателен только `@Документ`, остальные поля —
изменяемые. Проверено на практике:

```json
{
  "method": "Лид.Записать",
  "params": {
    "Запись": {
      "_type": "record",
      "f": 0,
      "d": [56224, "АТ: запись через RPC"],
      "s": [
        { "n": "@Документ", "t": "Число целое" },
        { "n": "Примечание", "t": "Строка" }
      ]
    }
  }
}
```

Ответ: `{"result": 56224}`. Повторное чтение подтвердило новое значение `Примечание`.

Перед сохранением карточка вызывает `Dokument.CheckUnique`:

```json
{ "method": "Dokument.CheckUnique", "params": { } }
```

Ответ `{"result": null}` означает отсутствие конфликтов уникальности.

> Важно: `Лид.Записать` **не меняет этап**. Передача `Лид.Фаза` и `Лид.Переход`
> в запись проходит без ошибки, но сервер оставляет прежнюю фазу. Смена этапа —
> отдельный сценарий (см. 6.1).

### 4.6. Удаление — `Документ.УдалитьДокументы` ✅

```json
{
  "method": "Документ.УдалитьДокументы",
  "params": { "ИдО": [56224] }
}
```

Ответ:

```json
{
  "result": {
    "_type": "record", "f": 0,
    "s": [
      { "n": "УдаленыВКорзину", "t": { "n": "Массив", "t": "Число целое" } },
      { "n": "УдаленыНасовсем", "t": { "n": "Массив", "t": "Число целое" } }
    ],
    "d": [[56224], []]
  }

```

После вызова `Лид.ПрочитатьДляУчастника` возвращает `Удален = true`.
Клиентский модуль `EDO3/Actions/Storage/deleteDocument` использует привязку
`destroy` из `Лид.TypeSettings` (для лида — `Документ.УдалитьДокументы`),
а для массового удаления передаёт массив `ИдО`.

### 4.7. Восстановление — `Документ.Восстановить` ✅

Последовательность (модуль `ActiveSales/leadRestore`):

1. `Документ.ПроверитьНаличиеНомераПоИдО` `{ИдО: 56224}` → `false`, если номер есть.
2. Если номера нет — `Документ.СоздатьНомерПоИдО` (⚠️).
3. При необходимости — `Лид.Записать` с новыми `Номер` / `ЧисловойНомер`.
4. `Документ.Восстановить` `{ключДокумента: 56224}`.

Проверено:

```json
{ "method": "Документ.Восстановить", "params": { "ключДокумента": 56224 } }
```

Ответ: `{"result": ""}`. После вызова `Удален = false`, номер `1800` сохраняется.

### 5.1. Товары

Вкладка «Товары» в карточке читает состав через сервис счёта:

```json
{
  "method": "СчетСкИсх.DocNomListForUser",
  "params": {
    "Фильтр": {
      "_type": "record", "f": 0,
      "d": [true, true, true, true, true, true, true, true, true,
            "WHDNomList/grid:config-v1-columns-WHDLead_OutBill-NomList",
            true, true, true, 56224, 0],
      "s": [
        { "n": "add_discounts_dn_info", "t": "Логическое" },
        { "n": "add_lids_bill_in_nom_rec", "t": "Логическое" },
        { "n": "add_lids_bill_in_totals_rec", "t": "Логическое" },
        { "n": "calc_access_editing_price", "t": "Логическое" },
        { "n": "calc_characteristic_params", "t": "Логическое" },
        { "n": "calc_item_type", "t": "Логическое" },
        { "n": "calc_modifiers", "t": "Логическое" },
        { "n": "calc_rp_add_fields_simple", "t": "Логическое" },
        { "n": "calc_shipped_full", "t": "Логическое" },
        { "n": "column_config_id", "t": "Строка" },
        { "n": "delete_lids_empty_bill", "t": "Логическое" },
        { "n": "init_selected_nom_set_data", "t": "Логическое" },
        { "n": "set_default_prices_for_present", "t": "Логическое" },
        { "n": "ЛидИд", "t": "Число целое" },
        { "n": "СкладскойДокумент", "t": "Число целое" }
      ]
    },
    "Сортировка": null,
    "Навигация": { "...": "..." },
    "ДопПоля": []
  }
}
```

Ключевой параметр — `Фильтр.ЛидИд = 56224`. Состав хранится не в самом лиде,
а в связанном счёте (`СчетИсх`): флаги `add_lids_bill_in_nom_rec` /
`delete_lids_empty_bill` управляют подмешиванием и очисткой пустого счёта.

Универсальный метод корзины `NomCatalogBasket.getBasket` ⚠️ требует параметр
`basketype`; без него сервер отвечает:

```
При вызове метода "NomCatalogBasket.getBasket" не передан аргумент "basketype"!
```

Точный набор параметров (`basketype` + идентификатор + режим) не подтверждён.

```json
    }
  }

```

Ответ — `recordset` документов с колонками `@Документ`, `ИдентификаторДокумента`,

### 6.1. Смена этапа ✅ (чтение) / ⚠️ (запись)

`CRMEvent.CreateMaster` и полный набор полей перехода.

### 6.2. Откат на предыдущий этап ⚠️

Откат использует тот же механизм, что и переход вперёд, но с обратным переходом:

- `CRMEvent.AvailableDocCommands` с `ex_params.phase_id = <текущая фаза>` вернёт
  доступные переходы, включая обратный (если он разрешён настройками темы);
- далее `CRMEvent.CreateMaster` → `CRMEvent.Write` → `Лид.Записать`.

Ограничение задаётся настройками темы: в исследованной теме «20 этапов 5+5»
переходы вперёд доступны, обратный переход нужно выбирать из списка доступных
команд — жёсткого «rollback»-метода нет.

### 6.3. Смена ответственного ⚠️

Клиентский модуль `ActiveSales/dealsActionsHandlers` для одиночной сделки
вызывает `CRMLead.FixPlan`, для массовой — `CRMLead.FixPlanMass`.

Массовая операция:

```json
{
  "method": "CRMLead.FixPlanMass",
  "params": {
    "ActionParams": {
      "params": {
        "leads": [56224],
        "face": 3722874,
        "dat_plan": null,
        "comment": "комментарий",
        "action": "fixation"
      }
    },
    "Operation": {
      "Scenario": "DealFixationAndPlan",
      "TaskName": "Fixaiton",
      "RegClass": "Лид",
      "Type": "ByOne",
      "ReturnField": "@Документ",
      "Channel": "crm.deals.updated"
    }
  }
}
```

Прямой вызов `CRMLead.FixPlan` с пустыми параметрами вернул
`Метод CRMLead.FixPlan/0 не найден или недоступен` — имя метода в этой версии
может отличаться или требовать другого сервиса. Массовый вариант подтверждён
только по коду клиента.

UI-точка входа: клик по блоку ответственного
`[data-qa="edo3-Sticker__mainInfo"]` → диалог «Изменить ответственного».

### 6.4. Согласование ❓

Метод `Согласование.Создать` зарегистрирован на сервере: прямой вызов вернул
не «метод не найден», а ошибку контракта:

```
В объекте нет поля Расширение
```

Это означает, что метод существует, но ожидает запись объекта «Согласование»
с полем `Расширение` (вложенная запись с параметрами согласования).
Полный контракт подобрать не удалось; UI-точка входа — меню карточки сделки
(пункт «Согласование»).

Методы `Документ.СоздатьСогласование`, `Документ.НаправитьНаСогласование`,
`Документ.Согласовать`, `Docflow.CreateApproval`, `Docflow.StartApproval`
на стенде не зарегистрированы.

## 9. Ограничения и открытые вопросы

1. **Смена этапа.** Нужен точный контракт `CRMEvent.Write` для перехода:
   какие поля `@Событие`, `Тип`, `Переход` обязательны и как сервер связывает
   событие с фазой лида.
2. **Откат.** Требуется тема с разрешённым обратным переходом; в текущей теме
   обратный переход не проверен.
3. **Смена ответственного.** Подтвердить `CRMLead.FixPlan` / `CRMLead.FixPlanMass`
   прямым вызовом с полным набором параметров.
4. **Согласование.** Подобрать структуру записи `Согласование` с полем `Расширение`.
5. **Товары.** Уточнить `basketype` и полный набор параметров
   `NomCatalogBasket.getBasket`; проверить запись состава (добавление/удаление строк).
6. **Права.** Часть методов зависит от лицензии CRM и роли пользователя;
   проверка выполнялась под `crmviewer`.
