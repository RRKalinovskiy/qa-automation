# Saby Checks API и поддержка MCP

## Когда использовать

- Нужно понять, каким JSON-RPC методом читать или писать проверку Saby.
- Нужно добавить инструмент в MCP `saby-checks`.
- Нужно разобрать ошибку «Внутренняя ошибка сервера» или «Документ недоступен».
- Нужно снять новый контракт с веб-клиента Saby.
- Нужно проверить, что MCP не сломался после изменений.

Полное исследование: `docs/api/sbis-checks.md`.

## Карта MCP

```text
mcp/saby-checks/
├── server.mjs      # регистрация MCP-инструментов
├── client.mjs      # Saby JSON-RPC, cookie, guid → id
├── checks.mjs      # доменные операции: check/stage/point/status
├── records.mjs     # record/recordset, транслитерация, длительности
├── statuses.mjs    # статусы и алиасы
└── test/           # unit + smoke
```

Запуск: `npm run mcp:saby`.
Конфигурация: `opencode.jsonc` → `mcp.saby-checks`.

## Транспорт

```text
POST {SABY_BASE_URL}/service/?x_version=26.5118-135
```

Заголовки, без которых методы не маршрутизируются:

| Заголовок | Значение |
|---|---|
| `x-adaptive` | `false` |
| `x-requested-with` | `XMLHttpRequest` |
| `x-calledmethod` | латиница, например `PunktProverki.Zapisat` |
| `x-originalmethodname` | `base64(UTF-8("<Сервис.Метод>"))` |
| `x-saby-appid` | `d7b1d6a5-e59d-4b03-b823-726fbdc35d09` |
| `x-saby-appversion` | `26.5118` |
| `x-saby-cfgid` | `2725babf-70e1-4f04-8e78-1b4272de7b21` |
| `x-lastmodification` | `YYYY-MM-DDTHHmmss.SSSSSS+03` |
| `x-osversion` | `OSType=Windows;OSVersion=10.0;IsWin11=true` |
| `cookie` | сессия Saby |

Авторизация:

1. `npm run saby:login` → `.auth/saby.json` (Playwright storageState);
2. или `SABY_COOKIE` — готовая строка Cookie.

`SABY_COOKIE` приоритетнее storageState.

## Ключевые поля

### Проверка

| Поле | Смысл |
|---|---|
| `@Документ` | числовой id проверки |
| `ИдентификаторДокумента` | guid |
| `ДокументРасширение.Название` | название в шапке |
| `РазличныеДокументы.ИнформацияJSON` | JSON-название, обновлять вместе с `Название` |
| `ОбъектПланирования.@ОбъектПланирования` | id шаблона (485 — «Тестирование проекта») |
| `Сотрудник`, `Подразделение` | ответственный и подразделение |
| `ЧеклистСтруктура.@ЧеклистСтруктура` | корень структуры |

### Пункт/этап

| Поле | Смысл |
|---|---|
| `@Документ` | id документа (для read/write/delete) |
| `ЧеклистСтруктура.@ЧеклистСтруктура` | id структуры (для дочерних) |
| `ЧеклистСтруктура.Название` | название |
| `ЧеклистСтруктура.Комментарий` | «Общее описание» → «Комментарий»: короткое, что проверяем |
| `ЧеклистСтруктура.Описание` | «Общее описание» → «Описание»: ПРЕДУСЛОВИЕ, ШАГИ, РЕЗУЛЬТАТ |
| `ЧеклистСтруктура.Версия` | «Текущее состояние»: только комментарий статуса |
| `ЧеклистСтруктура.Раздел` | `[id структуры родителя]` |
| `ЧеклистСтруктура.ОбъектПланирования` | id статуса |
| `ЧеклистСтруктура.ПлановоеВремя` | ISO-длительность |
| `ЧеклистСтруктура.Лицо` | ответственный |

### Типы пунктов

Тип хранится только в названии (`ТК:` / `ЧЛ:` / `Т:`); отдельного поля типа
в API нет.

| Префикс | Смысл | Обязательное условие |
|---|---|---|
| `ТК` | тест-кейс, обычно автотест | `automation` не обязателен; до 10 шагов рекомендуется, больше 15 — повод для дробления |
| `ЧЛ` | набор идей одного ручного сценария | минимум 2 идеи/шага |
| `Т` | требование | — |

Правило по умолчанию — `ЧЛ`. `ТК` — один тест-кейс, обычно автотест;
ссылка на автотест не обязательна. `manual: true` помечает ручной `ТК`
(пометка ПК вместо АТ).

`automation` сейчас попадает в «Описание» блоком `АВТОТЕСТ:`; отдельного
поля в Saby нет. Пометки MCP только рекомендует (по умолчанию `pc` для `ЧЛ`,
`automated` для `ТК`), но не записывает: частичная запись `Пометки`
игнорируется.

План слияния дублей строит `saby_check_merge_plan` — read-only. Он читает
пункты через `ПрочитатьДляУчастника`, группирует идеи и предлагает шаги,
но не создаёт и не удаляет документы. Для записи шагов нужен отдельный
контракт `TestCase` (в MCP пока не реализован).

## Правила идентификаторов

- `@Документ` ≠ `@ЧеклистСтруктура`.
- Для `ПрочитатьДляУчастника`, `Записать`, `УдалитьДокументы` — `@Документ`.
- Для `СписокПунктовПроверки` и создания дочерних — `@ЧеклистСтруктура`.
- Этап и пункт — один тип `ПунктПроверки` (`2745`).
- Корневой этап через API не создаётся; `Раздел = null` → ошибка.

## Подводные камни

| Симптом | Причина | Решение |
|---|---|---|
| `404` + «Внутренняя ошибка» | нет `x-lastmodification` или неверный `x-calledmethod` | добавить оба заголовка |
| Дата отклоняется | передан `DD.MM.YYYY` | только `YYYY-MM-DD` |
| Этап создался как пункт | неверные `Раздел$`/`Раздел@` | для этапа оба `true`, для пункта оба `false` |
| Не видно дочерних | передан `docId` вместо `structureId` | использовать `@ЧеклистСтруктура` |
| Счётчик этапа завышен | удалили документ, но не структуру | `ПунктПроверки.Remove` по id структуры |
| `Пометки` не применяются | частичная запись `Пометки` игнорируется | выставить в UI или полной записью документа |
| Данные сценария в поле статуса | перепутаны `Версия` и `Описание` | сценарий — в `ЧеклистСтруктура.Описание`, `Версия` — только статус |
| Название без `ТК/ЧЛ/Т` | нарушены правила оформления | `saby_check_rules`, префикс обязателен |
| `ТК` без `automation` | ссылка на автотест не обязательна | это допустимо; при необходимости добавьте файл/ссылку |
| `ЧЛ` с одной идеей | слишком мелкая единица, плодит карточки | добавить шаг в существующий `ЧЛ` |
| В `ТК` больше 15 шагов | тест слишком длинный | разделить на несколько `ТК` или перенести идеи в `ЧЛ` |
| Похожие `ТК` в разделе | дубли одной идеи | `saby_check_merge_plan`, затем слияние после подтверждения |
| Название не меняется | обновлено только `ДокументРасширение.Название` | обновить и `РазличныеДокументы.ИнформацияJSON` |
| `ПунктПроверки.Создать` вернул объект | этап возвращает `record`, пункт — число | нормализовать через `extractId` |
| Статус не изменился | вызван `Записать` вместо массового метода | `Проверка.МассовоеИзменениеСтатусаИзПМО` |
| «Документ недоступен» | неверный guid, удалён или нет прав | проверить ссылку/доступ |

## Как добавить инструмент

1. Добавь доменный метод в `checks.mjs` (без MCP-деталей).
2. Зарегистрируй инструмент в `server.mjs`:

   ```js
   server.registerTool(
     'saby_check_example',
     {
       title: '...',
       description: '...',
       inputSchema: z.object({ check: checkRef }),
     },
     async ({ check }) => {
       try {
         const value = await getService().example(check);
         return ok(value);
       } catch (error) {
         return fail(error);
       }
     },
   );
   ```

3. Добавь unit-тест в `test/service.test.mjs` с фейковым клиентом.
4. Прогони `npm run test:mcp` и `node mcp/saby-checks/test/mcp-smoke.mjs`.
5. Обнови `docs/api/sbis-checks.md` и навык `saby-checks`.

## Как снять новый контракт с UI

1. Открой карточку проверки в браузере.
2. Сними `browser.network.list` до действия.
3. Выполни действие (создать пункт, сменить статус).
4. Найди новый запрос к `/service/`, прочитай `x-calledmethod`,
   `requestBody.text`, `responseBody.text`.
5. Повтори вызов напрямую с теми же заголовками.
6. Перечитай объект и проверь побочный эффект.
7. Помечай метод: ✅ проверен, ⚠️ только трафик, ❓ контракт неизвестен.

Полезно: SSR-страница `/doc/<guid>` содержит `"entityKey":"<id>"` —
это числовой id проверки.

## Тесты

```bash
npm run test:mcp          # unit + smoke
npm run saby:session      # проверить авторизацию
npm run typecheck         # общий typecheck проекта
```

Smoke-тест не требует Saby: он проверяет `initialize` и `tools/list`.
Unit-тесты используют фейковый клиент и локальный HTTP-мок.

## Чек-лист

- [ ] Метод проверен прямым вызовом, а не только по трафику.
- [ ] Заголовки `x-calledmethod` и `x-originalmethodname` согласованы.
- [ ] `x-lastmodification` присутствует.
- [ ] `record` собран по `s`/`d`, а не объектом.
- [ ] `@Документ` и `@ЧеклистСтруктура` не перепутаны.
- [ ] После записи объект перечитан.
- [ ] Тесты MCP зелёные.
- [ ] Документация и навык обновлены.
