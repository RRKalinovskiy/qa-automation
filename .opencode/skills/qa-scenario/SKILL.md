# Проектирование тест-сценариев

## Когда использовать

- Нужно разобрать новую фичу или требования.
- Нужно написать, дополнить или отревьюить тест-сценарии.
- Нужно оценить полноту покрытия и выбрать, что автоматизировать.
- Нужно обновить матрицу «требование → сценарий → автотест».

## Входы

1. Требования, user story, макеты, описание API.
2. OpenAPI-спецификация или коллекция Postman.
3. Доступ к стенду (если есть) для проверки поведения.
4. Существующие сценарии и автотесты, чтобы не дублировать покрытие.

Если входов не хватает — не выдумывай поведение. Зафиксируй допущение и открытый вопрос.

## Процесс

1. **Собери контекст.** Выпиши акторов, экраны, эндпоинты, состояния и ограничения.
2. **Построй карту функционала.** Разбей область на блоки: создание, чтение, изменение, удаление, права, ошибки.
3. **Сгенерируй проверки по классам** (см. таблицу ниже).
4. **Опиши каждый сценарий** по шаблону `docs/scenarios/_template.md`:
   - ID `TC-<AREA>-<NNN>`, цель, приоритет;
   - предусловия и данные;
   - шаги с однозначным ожидаемым результатом;
   - постусловия и открытые вопросы.
5. **Расставь приоритеты** от критичного пользовательского пути к редким граничным случаям.
6. **Выбери уровень автоматизации:**
   - API — бизнес-правила, контракты, негативные ответы, подготовка данных;
   - UI — только пользовательские пути и то, что нельзя проверить через API;
   - оба — сквозной путь, где важен и результат, и отображение.
7. **Обнови трассировку** в `docs/scenarios/README.md`.

## Классы проверок

| Класс | Что проверяем |
|---|---|
| Позитивный | Основной путь с валидными данными. |
| Негативный | Неверные данные, недопустимые состояния, отказы. |
| Граничный | Минимум, максимум, пусто, длина, округление, даты. |
| Права доступа | Роли, чужие объекты, отсутствие авторизации. |
| Идемпотентность | Повторный запрос, двойной клик, повторная отправка. |
| Восстановление | Сеть, таймаут, 5xx, повтор после ошибки. |
| Совместимость | Браузеры, разрешения, локализация (для UI). |

## Правила

- Один сценарий — одна проверяемая цель.
- Ожидаемый результат должен быть проверяемым: конкретный статус, текст, состояние, запись в БД.
- Данные не дублируются в шагах и в блоке данных — используй ссылку на набор `TD-…`.
- Негативные кейсы не смешивай с позитивными.
- Не описывай реализацию («нажать по CSS-селектору»), описывай поведение.
- Для каждого сценария указывай, что будет с данными после теста.

## Результат

- Файл `docs/scenarios/<area>.md` по шаблону `docs/scenarios/_template.md`.
- Обновлённая матрица трассировки.
- Список кандидатов на автоматизацию с уровнем (API/UI).
- Список открытых вопросов владельцу требований.

## Чек-лист

- [ ] Покрыты позитивный путь, негатив и границы.
- [ ] Проверены права доступа и чужие объекты.
- [ ] У каждого сценария есть ID, приоритет и статус.
- [ ] Данные описаны и очищаются.
- [ ] Ожидаемые результаты проверяемы.
- [ ] Нет дублей с существующими тестами.
- [ ] Открытые вопросы зафиксированы.
