# Тестовые данные

## Когда использовать

- Новому сценарию нужны данные.
- Тесты падают из-за общего изменяемого стенда.
- Нужно добавить фабрику, фикстуру или очистку.
- Нужно проверить, что в репозиторий не попадают секреты и персональные данные.

## Принципы

1. **Уникальность на прогон.** Префикс `qa-` + короткий UUID или timestamp.
2. **Изоляция.** Тест создаёт свои данные и не зависит от порядка запуска.
3. **Воспроизводимость.** Данные создаются кодом или API, а не руками.
4. **Управляемая очистка.** Владелец набора и способ удаления известны заранее.
5. **Безопасность.** Только синтетика; секреты — в `.env`.

## Процесс

1. **Выпиши поля** сущности и бизнес-ограничения (форматы, длины, уникальность, связи).
2. **Выбери класс данных:**

   | Класс | Когда |
   |---|---|
   | Справочные | Значения стабильны и общие для стенда. |
   | Генерируемые | Нужна уникальность на каждый прогон. |
   | Сид-данные | Сущность уже есть на стенде, менять её нельзя. |
   | Секреты | Токены и пароли, только `.env`. |

3. **Создай фабрику** в `src/data/factories/<entity>.ts`:
   - функция `build<Entity>(overrides: Partial<Entity> = {})`;
   - валидные значения по умолчанию;
   - уникальный идентификатор в критичных полях;
   - никаких обращений к сети внутри фабрики.
4. **Определи подготовку.** Предпочтительно через API — быстрее и стабильнее UI. Для UI-тестов используй API-хелпер в `beforeEach` или фикстуру.
5. **Определи очистку.** `afterEach`/`afterAll` с удалением даже при падении теста. Если удаления нет — отдельный аккаунт и префикс `qa-`.
6. **Зарегистрируй набор** в `docs/test-data/<area>.md` по шаблону и добавь строку в реестр `docs/test-data/README.md`.

## Пример фабрики

```ts
import { randomUUID } from 'node:crypto';

export type TestUser = {
  email: string;
  password: string;
  name: string;
};

export function buildTestUser(overrides: Partial<TestUser> = {}): TestUser {
  const id = randomUUID().slice(0, 8);

  return {
    email: `qa+${id}@example.com`,
    password: `Qa!${id}${id}`,
    name: `QA ${id}`,
    ...overrides,
  };
}
```

## Правила

- Email — только домен `example.com`.
- Телефоны — только `+1 555 …`.
- Пароли генерируются и не переиспользуются между наборами.
- Суммы, лимиты и даты задаются явно, а не «как получится».
- Данные, созданные тестом, помечаются префиксом `qa-`, если есть риск пересечения.
- Не изменяй общие сид-данные; создавай копию.
- В логах и отчётах маскируй токены и персональные поля.

## Очистка

```ts
test.afterEach(async ({ request }) => {
  if (!createdId) return;
  await request.delete(`/users/${createdId}`);
  createdId = undefined;
});
```

- Очистка должна быть идемпотентной: повторное удаление не должно ронять тест.
- Если teardown упал, тест всё равно должен показать исходную ошибку.
- Для параллельных прогонов не используй фиксированные email/логины.

## Чек-лист

- [ ] Данные уникальны для каждого прогона.
- [ ] Есть фабрика с валидными значениями по умолчанию.
- [ ] Подготовка идёт через API, а не через UI (где возможно).
- [ ] Очистка выполняется при падении.
- [ ] Нет реальных персональных данных и секретов.
- [ ] Набор зарегистрирован в `docs/test-data/`.
